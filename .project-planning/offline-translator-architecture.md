# نقشهٔ مترجم آفلاین فارسی و روسی

## هدف

یک سامانهٔ کاملاً آفلاین برای این مسیرها:

1. گفتار فارسی یا روسی → متن با زبان تشخیص‌داده‌شده
2. متن فارسی ↔ متن روسی
3. متن فارسی یا روسی → گفتار همان زبان
4. حالت مکالمهٔ زنده با زیرنویس، ترجمه و پخش صوتی

تمام مدل‌ها پس از نصب از دیسک خوانده می‌شوند و اجرای عادی به اینترنت نیاز ندارد.

## معماری پیشنهادی

```text
Microphone / audio file
        |
   VAD + chunking (Silero VAD)
        |
   STT (Whisper multilingual, faster-whisper or whisper.cpp)
        |
 normalized transcript + confidence + language
        |
  translation router (fa↔ru, optional same-language bypass)
        |
 translated text + alternatives
        |
 TTS router (Russian voice / Persian voice)
        |
 audio stream or WAV output
```

هر مرحله باید API مستقل داشته باشد تا بتوان مدل را بدون تغییر رابط کاربری عوض کرد. برای شروع یک سرویس Python/FastAPI و یک کلاینت سادهٔ وب/موبایل کافی است. پردازش زنده باید با صف کوتاه، شمارهٔ قطعه و timestamp انجام شود تا پاسخ‌ها به‌ترتیب پخش شوند.

## انتخاب مدل‌ها

### گفتار به متن

- `whisper.cpp` برای اجرای کم‌مصرف CPU و بسته‌بندی ساده؛ مدل multilingual در قالب GGML/GGUF.
- `faster-whisper` برای GPU یا CPU قوی؛ مدل‌های Whisper را با CTranslate2 اجرا می‌کند.
- مدل پایهٔ پیشنهادی MVP: `small` یا `medium` چندزبانه. برای موبایل/CPU ضعیف از `base` شروع شود.
- فعال‌سازی VAD، تشخیص زبان و punctuation؛ زبان را به‌صورت اجباری روی `fa` یا `ru` هم قابل تنظیم کنید تا خطای تشخیص در قطعات کوتاه کم شود.

Whisper برای فارسی و روسی قابل‌استفاده است، اما باید با نمونه‌های واقعی کاربر ارزیابی شود؛ واژه‌های تخصصی و نویز محیطی معیار انتخاب مدل بزرگ‌تر هستند.

### ترجمه

- گزینهٔ سبک و مستقیم برای MVP: مدل‌های OPUS-MT/Helsinki-NLP برای `fa→ru` و `ru→fa`، در صورت موجود بودن نسخهٔ دقیق زبان.
- گزینهٔ باکیفیت‌تر و سنگین‌تر: `facebook/nllb-200-distilled-600M` با کدهای `pes_Arab` و `rus_Cyrl`؛ مدل کاملاً محلی است ولی حافظه و زمان بیشتری می‌خواهد.
- متن ورودی باید نرمال‌سازی شود (فاصلهٔ فارسی، نیم‌فاصله، اعداد و علائم) و خروجی با حفظ پاراگراف/زمان‌بندی ذخیره شود.
- ترجمهٔ خودکار را با امتیاز اطمینان و امکان اصلاح دستی نمایش دهید؛ برای اصطلاحات ثابت یک glossary محلی اضافه کنید.

### متن به گفتار

- روسی: Piper با voice روسی، یا Silero TTS روسی؛ هر دو برای اجرای محلی مناسب‌اند.
- فارسی: ابتدا یک مدل VITS/MMS-TTS فارسی سازگار با Transformers آزمایش شود؛ اگر کیفیت یا مجوز مناسب نبود، eSpeak NG/RHVoice به‌عنوان fallback کم‌حجم در نظر گرفته شود.
- هر voice باید metadata شامل زبان، گوینده، sample rate و مجوز داشته باشد. خروجی استاندارد داخلی WAV/PCM باشد و سپس در صورت نیاز به Opus تبدیل شود.
- کیفیت فارسی باید با مجموعهٔ جمله‌های ثابت (اعداد، نام‌ها، جمله‌های محاوره‌ای) ارزیابی شود؛ وجود مدل فارسی را قبل از انتشار به‌عنوان قابلیت قطعی اعلام نکنید.

## حالت‌های محصول

1. **فایل صوتی:** آپلود WAV/MP3، نمایش متن اصلی، ترجمه و فایل‌های صوتی خروجی.
2. **زیرنویس زنده:** قطعه‌های ۱ تا ۳ ثانیه‌ای، نمایش متن موقت و نهایی، ترجمه پس از نهایی‌شدن قطعه.
3. **مکالمه:** کانال A/B یا push-to-talk برای جلوگیری از ترجمهٔ صدای خروجی خود سامانه.
4. **حریم خصوصی:** عدم ارسال صوت یا متن به شبکه؛ پاک‌سازی فایل‌های موقت و امکان اجرای کامل در حالت airplane mode.

## معیارهای پذیرش MVP

- روی CPU معمولی، قطعهٔ ۵ ثانیه‌ای در زمان قابل‌قبول پردازش شود؛ latency هدف زنده کمتر از ۲ تا ۴ ثانیه.
- برای ۲۰ جملهٔ فارسی و ۲۰ جملهٔ روسی ضبط‌شده، نرخ خطای واژه و خطای ترجمه ثبت شود.
- هر دو جهت ترجمه و هر دو صدای TTS بدون شبکه اجرا شوند.
- قطع و وصل قطعه‌ها باعث جابه‌جایی ترتیب یا تکرار متن نشود.
- مدل‌ها، checksum، مجوز و حجم دیسک در manifest ثبت شوند.

## مراحل اجرایی

### مرحلهٔ ۰ — نمونهٔ خط فرمان

یک CLI بسازید که یک فایل صوتی را بگیرد و JSON شامل زبان، متن، ترجمه و مسیر WAV خروجی برگرداند. ابتدا با Whisper `small`، NLLB یا OPUS-MT و یک voice روسی/فارسی آزمایش شود.

### مرحلهٔ ۱ — سرویس محلی

ماژول‌های `stt`, `translation`, `tts`, `pipeline` و `models` جدا شوند. FastAPI endpointهای health، transcribe، translate و synthesize داشته باشد. مدل‌ها lazy-load و در حافظه cache شوند.

### مرحلهٔ ۲ — رابط زنده

WebSocket برای قطعه‌های صوتی، VAD، متن موقت/نهایی و صف پخش اضافه شود. تنظیمات مدل و زبان در فایل محلی قابل تغییر باشد.

### مرحلهٔ ۳ — بهینه‌سازی و بسته‌بندی

کم‌حجم‌سازی/quantization، اجرای CPU، بستهٔ دسکتاپ یا Android، تست airplane mode، لاگ‌گیری محلی و import/export مدل‌ها انجام شود.

## ریسک‌ها و تصمیم‌های باز

- کیفیت TTS فارسی احتمالاً گلوگاه اصلی است؛ باید چند مدل با مجوز روشن روی دادهٔ ثابت مقایسه شوند.
- NLLB کیفیت خوبی دارد ولی روی موبایل سنگین است؛ OPUS-MT برای MVP سبک‌تر است.
- مجوز مدل و voice جداگانه بررسی شود؛ مجوز کد به‌تنهایی مجوز وزن مدل یا دادهٔ صوتی نیست.
- برای استفادهٔ تجاری، شرایط Whisper، NLLB، OPUS-MT، Piper/Silero و voice فارسی انتخاب‌شده در manifest و مستندات ثبت شود.
- قبل از حذف کامل مخزن قبلی، یک commit یا archive قابل‌بازگشت نگه داشته شود؛ پاک‌سازی GitHub فقط پس از بازبینی نهایی و با push صریح انجام شود.
